## Implemented boundaries

- Existing createOrderV3 unpaid creation, immutable supplier reference, durable
  CAS claims and read-first recovery are retained. Unknown outcomes do not retry.
- Newly dispatched unpaid orders stop before parent creation, allowing finance
  staff to select 1–20 independent orders. One documented addCart / addCartConfirm /
  saveGenerateParentOrder sequence creates a shared parent. Exact membership,
  individual current amounts, stock/freight and total are checked before exposing
  the official `mine/payment?pid=` link. Concurrent clicks cannot repeat the claim.
- Each order keeps its individual USD product/shipping/tax amounts and CJ order
  identity. Every member must be independently reconciled before a batch settles.
  Shared card parents cannot receive per-order wallet grants or wallet debits.
- Existing independent payment links are never silently reparented. Interrupted
  parent requests, expired links and price/stock/freight changes stay held for
  review; the application does not invent a payment lookup or renewal endpoint.
- Authenticated CJ order detail and valid paymentDate prove card payment. A
  browser return or webhook payload never proves payment. Wallet reconciliation
  additionally requires the exact successful billing entry.
- Saudi mobile, street, building and four-letter/four-digit national short
  address are required before new checkout and bank handoff. House number is
  transmitted explicitly; national address remains in the full shipping address.
- Official `sign` header: Base64 HMAC-SHA256 over raw body with the account openId.
  Configure `CJ_WEBHOOK_OPEN_ID` and activate the relevant CJ callback topic.
  Legacy configured signature/secret headers remain supported. Durable storage
  precedes HTTP success; provider reconciliation runs after acknowledgment.
- Existing five-minute timer now invokes batch detail reconciliation, including
  unpaid/uncertain payment identities while new purchasing is disabled. Batch API
  validation accepts up to 100 IDs; each scheduled pass is bounded to 10 oldest
  active records. The installed runner's checked=0/1 response contract is retained.
  Capacity and timer activity must be checked operationally; this is not a promise
  that an unbounded backlog can be reconciled within one hour.
- CJ Delivered/Completed is delivery evidence. Pickup, delivery attempt and
  tracking-number presence are not. Failed/returned shipments and CJ disputes
  raise review holds. A customer can record a delivery objection; its immutable
  reason is visible to authorized order/shipping staff and blocks closure and
  financial dispatch. Holds survive subsequent payment reconciliation.

## Deliberately manual / not live-proven

- Visa/Mastercard availability and one real transaction covering ten orders must
  be verified on this CJ account at the actual cashier; simulation is not proof.
- CJ order-creation entitlement, callback subscription and the production timer's
  active state have not been changed or asserted by these code-only changes.
- Post-payment stockout, supplementary shipping approval, refunds, dispute
  adjudication and clearance of a customer objection require authorized human
  handling with CJ. No automatic supplementary debit, refund, cancellation,
  dispute submission, or automatic release of a disputed hold is enabled.
- Carrier-specific signed POD is not guaranteed. Do not advertise it for a route
  without proof from that carrier. A real delivered order remains to be tested.

## Test scope

New tests cover one/ten shared parent memberships, partial rejection, expiry,
unknown response, concurrent durable claims, amount mismatch, strict Saudi
address, signed webhook persistence/acknowledgment, polling identity, customer
objection, retained holds and prevention of per-member shared-parent wallet debit.
Isolated MySQL tests exercise batch persistence and concurrent claims. No
production database schema or media migration is introduced.
