# خطة إعادة البناء الجذري لمنصة تربّح (v2)

> **المبدأ:** الكود الحالي هو المواصفات (Spec). الاختبارات تحفظ سلوكه، ثم نعيد البناء حتى تنجح جميعها — دون أن يتوقف الموقع الحي يوماً واحداً.

---

## 1) تشخيص الوضع الحالي (لماذا نعيد البناء)

قياس فعلي من المستودع بتاريخ هذه الخطة:

| المؤشر | القيمة | الحكم |
|---|---|---|
| ملفات TS/TSX | 183 | حجم متوسط قابل للإدارة |
| صفحات (routes) | 63 | — |
| ملفات اختبار | **0** | 🔴 لا شبكة أمان إطلاقاً |
| استدعاءات SQL خام (`$queryRawUnsafe`/`$executeRawUnsafe`) | **193** | 🔴 بلا فحص أنواع، هشّة أمام تغيّر المخطط |
| صفحات `force-dynamic` | **61 من 63** | 🔴 لا caching — كل زيارة تضرب قاعدة البيانات |
| هجرات قاعدة بيانات (migrations) | 0 — بدلها `ensure()` بـ `ALTER TABLE` عند التشغيل | 🔴 المخطط يتشكّل وقت التشغيل بلا سجل |
| CI (فحص تلقائي عند الدفع) | لا يوجد | 🔴 الجودة تعتمد على الفحص اليدوي |

### الديون التقنية المحددة بالاسم
1. **`ensure()` الذاتية** في `merchant.ts`, `moderation.ts`, `roles.ts`...: أعمدة وجداول تُنشأ بـ ALTER/CREATE عند أول طلب — لا نعرف شكل قاعدة البيانات إلا بقراءة الكود.
2. **Singletons بالذاكرة** (`let ensured = false`, `rolePermCache`): تنكسر عند تشغيل أكثر من نسخة (scale-out) أو إعادة تشغيل.
3. **N+1 queries**: `adminStoreList()` تنفّذ 4 استعلامات لكل متجر؛ `homeFeaturedAds()` تستدعي `getMyAds` لكل تاجر.
4. **خلط الطبقات**: صفحات تحوي SQL، ومنطق أعمال داخل server actions مباشرة.
5. **`getMyAds(s.userId)` في واجهة المتجر** تجلب كل إعلانات التاجر ثم تُفلتر بالذاكرة.
6. **بيئة التطوير تُعاد تهيئتها** — أي عمل غير مدفوع للفرع يضيع (موثّق ومتكرر).

## 2) جرد النظام = المواصفات (ما يجب أن تحفظه الاختبارات)

### أ. الجمهور العام
- الرئيسية: أقسام منسدلة متعددة الاختيار، أقسام الاهتمام مثبّتة، متاجر مميّزة، مبوّبة، إحصائيات قابلة للتهيئة، بانرات ترويجية.
- البحث والأقسام وتفاصيل الإعلان: صور/فيديو/صوت، خرائط + مسافة من الزائر، واتساب (`wa.me/966…`)، تعليقات، مشابهة، QR.
- المبوّبة + المصمم الذكي + سبلاش الدخول.
- المتاجر: **واجهة مستقلة تماماً** (ChromeGate يخفي هيكل الموقع)، قوالب تخطيط ×6، تيمات ×20، كتالوج ×4 أشكال بحقول قابلة للتبديل، متابعة/تقييم/تعاون بين متاجر/عرض بالرئيسية، شروط وتعهّد موثّق بتاريخه، بحث داخلي، شارات (موثّق/مستوى/منذ سنة/تخصص).

### ب. العضو
- حساب: دخول بأي صيغة جوال + `?next=` للرجوع، تسجيل بموافقة الشروط، نسيت كلمة المرور عبر SMS.
- إعلاناتي (تعديل/حذف ضمن نافذة زمنية)، مفضلة، مراسلات (حذف رسالة بفترة سماح — يختفي عند الطرفين)، تحليلات بائع، اهتمامات، توثيق، اختيار تصميم الموقع (6 هويات)، متجري.

### ج. الإدارة (20+ صفحة)
مستخدمون (تصنيف الكل/نشط/محظور + حظر مؤقت بالأيام/دائم)، إدارة المتاجر (اعتماد/إيقاف/حذف مقيّد النطاق/إنذارات)، أدوار (مصفوفة قابلة للتحرير + «مراقب متاجر تربّح» المعزول)، إعلانات (موافقة/أرشفة/حذف الكل)، مكررة، مبوّبة، كلمات وحارس محتوى، بلاغات (المُبلّغ سرّي + ردّ صاحب الإعلان)، مراقبة مراسلات، توثيقات، باقات، ترويجية، نسخ احتياطي/استعادة، إعدادات، بوابات SMS، دليل إدارة.

### د. قواعد العمل الحرجة (كل واحدة = اختبار إلزامي)
1. طلب بلا سعر يعرض «مطلوب» — **أبداً** «على السوم».
2. صاحب متجر معتمد ⇒ إعلاناته تُنشر مباشرة متجاوزة إعداد المراجعة العام.
3. الإنذار الثالث للمتجر ⇒ إيقاف تلقائي، والإنذارات السابقة محفوظة.
4. الحظر المؤقت يُرفع تلقائياً بانقضاء مدته (دخول/نشر/قوائم).
5. prefetch لرابط الخروج **لا** يُنهي الجلسة.
6. محتوى غير أخلاقي (نص أو صورة عبر nsfwjs) ⇒ حظر فوري؛ مخدرات/سلاح/سياسي ⇒ سترايك ثم حظر عند الثانية.
7. مكرر ذاتي/إغراق/حشو كلمات ⇒ منع نشر بعدّاد محاولات.
8. متجر غير معتمد: يراه مالكه والإدارة فقط؛ الجمهور يرى صفحة «قيد المراجعة» وليس 404.
9. «مراقب متاجر تربّح» يصل لإدارة المتاجر **فقط**، وحذف المتجر لا يمسّ حساب العضو أو إعلاناته.
10. فتح متجر جديد يتطلب تعهّد الشروط (client+server) ويُختم بتاريخه.
11. جلسات الأعضاء `Cache-Control: private, no-store` (لا صفحة مخبّأة لمجهول تُقدَّم لعضو).
12. معرّفات غير رقمية في المسارات ⇒ 404 نظيفة لا 500.
13. كلمات مرور Laravel القديمة (`$2y$`) تعمل كما هي.
14. الشعار المائي «تربح» يُحرق في صور الإعلانات، والملفات content-addressed.

> «كل شيء» غير قابل للحصر في دفعة واحدة — نبدأ بهذه القائمة (النواة الصلبة) ونوسّع التغطية مع كل مرحلة.

## 3) البنية المستهدفة (ما معنى 10x هنا)

```
src/
  domain/            ← منطق الأعمال الصافي (قابل للاختبار بلا DB)
    moderation/  merchant/  roles/  ads/  pricing.ts ...
  data/              ← Prisma فقط: schema.prisma بهجرات مرقّمة، صفر SQL خام خارجها
  app/               ← صفحات رقيقة: تقرأ من domain وتعرض
  tests/
    unit/            ← Vitest: قواعد العمل (القائمة د أعلاه)
    integration/     ← Vitest + MySQL (testcontainers): طبقة البيانات
    e2e/             ← Playwright: رحلات حرجة (تسجيل→نشر→متجر→حظر)
```

1. **الاختبارات أولاً**: Vitest + Playwright (المثبّت أصلاً) + CI بـ GitHub Actions يشغّل `tsc + eslint + tests` على كل دفعة.
2. **قاعدة البيانات**: `prisma migrate` بسجل هجرات حقيقي؛ حذف كل `ensure()` بعد توليد baseline من الواقع الحالي؛ الـ193 استدعاء خام تنكمش إلى طبقة `data/` مفحوصة الأنواع.
3. **الأداء**: إصلاح N+1 (استعلام مجمّع واحد لقوائم الإدارة والمتاجر)، `unstable_cache`/`revalidateTag` بدل force-dynamic في الصفحات العامة (الرئيسية/الأقسام/المتاجر) — هدف: TTFB أقل من النصف وحمل DB أقل بـ10x فعلياً.
4. **الصلابة**: إلغاء الكاش بالذاكرة لصالح Redis الموجود أصلاً؛ rate limiting على actions الحساسة؛ تدوير الأسرار.
5. **الملاحظة**: request logging منظّم + التقاط أخطاء الخادم.

## 4) استراتيجيتا تنفيذ — والتوصية

### المسار أ — إعادة بناء تدريجية تحت الاختبارات (Strangler) ✅ **الموصى به**
كل مرحلة تُدفع وتُنشر والموقع حيّ طوال الوقت:

| المرحلة | المحتوى | معيار النجاح | الحالة |
|---|---|---|---|
| 0 | تهيئة Vitest + Playwright config + GitHub Actions | CI أخضر على الفرع | ✅ (اختبارات e2e لاحقاً — تحتاج DB اختبار) |
| 1 | **اختبارات توصيف** لقواعد العمل الـ14 + رحلات e2e الحرجة | السلوك الحالي محفوظ رقمياً | 🟡 35 اختباراً (تسعير/نص/متاجر/أدوار) — **اصطاد أول خطأ حقيقي** في normalizeAr |
| 2 | Prisma baseline migration + استئصال `ensure()` + طبقة `data/` | صفر SQL خام خارج `data/`، الاختبارات خضراء | 🟡 DDL موحّد في `data/schema-sync.ts` يعمل عند الإقلاع؛ schema.prisma مصدر الحقيقة؛ **merchant + moderation + roles صفر SQL خام** (إجمالي src: 193→107)؛ N+1 في adminStoreList أُصلح (1+4N→6)، وupsert أسقط استعلامات المتابعة في العدّادات؛ بقية الوحدات تباعاً |
| 3 | استخراج `domain/` (moderation, merchant, roles, pricing) وإعادة كتابتها | نفس الاختبارات خضراء على الكود الجديد |
| 4 | أداء: إصلاح N+1 + caching للصفحات العامة | قياس قبل/بعد موثّق | 🟡 بدأت: أحدث/مميّزة/الأكثر مشاهدة/واجهة المتاجر مُخزّنة في Redis بنمط `cached()` المجرَّب (TTL 60–120ث بلا نقاط إبطال قابلة للانجراف) — الرئيسية الآن شبه بلا استعلامات في الزيارات المتتابعة |
| 5 | تنظيف الصفحات لتصبح رقيقة + توسيع تغطية الاختبارات | — |

**لماذا هذا هو «إعادة البناء من الصفر» الصحيح:** كل طبقة تُعاد كتابتها فعلاً من الصفر (domain, data)، لكن تحت حراسة اختبارات تلتقط السلوك القديم — وهو حرفياً «اكتب اختبارات تحفظ ما يفعله، ثم كرّر حتى ينجح الجديد فيها كلها»، مطبَّقاً بطريقة لا تعرّض موقعاً حياً ببيانات حقيقية للخطر.

### المسار ب — إعادة كتابة كاملة على فرع v2 منفصل
- **المخاطر:** تجميد ميزات لأسابيع (وأنت ترسل طلبات تطوير يومياً)، انجراف المواصفات أثناء الكتابة، بيئة العمل هذه تفقد أي عمل غير مدفوع بين الجلسات، وخطر كلاسيكي بفقدان تكافؤ الميزات (63 صفحة).
- **متى يصحّ:** لو أردنا تغيير التقنية جذرياً. لسنا كذلك — Next.js 15 + Prisma حديثة أصلاً؛ المشكلة في الطبقات لا في الإطار.
