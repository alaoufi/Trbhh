# تكامل Salla في تربح — نسخة اختبار، 2026-09-19

## الحالة وحدود التشغيل

التنفيذ فوق Next.js/Prisma/MySQL ونظام الموردين والطلبات والدفع الحالي، وليس تطبيقًا بديلًا. الفرع المحلي `codex/salla-integration-20260919`. لا يتضمن هذا العمل نشرًا على الإنتاج، إرسال تطبيق Salla للمراجعة، شراءً حقيقيًا، تغيير مفاتيح البنك، أو نقل بيانات الإنتاج إلى قاعدة تجريبية.

الربط والمزامنة والتسعير والإدارة وWebhooks والحجز ومحاكاة الطلبات قابلة للاختبار. **إرسال طلب شراء حقيقي إلى Salla محجوب في الكود** حتى استكمال عقد المورد للشحن والعميل والتسوية واختباره. تغيير `SUPPLIER_ALLOW_LIVE_ORDERS` وحده لا يزيل هذا الحجب. بوابة شراء السلع في تربح الحالية لا تزال غير مسجلة للتشغيل؛ لم يغير التكامل ذلك.

## الروابط المنفذة

عند نشر هذه النسخة على `trbhh.sa` وضبط `SUPPLIER_PUBLIC_ORIGIN=https://trbhh.sa`:

- Callback: `https://trbhh.sa/api/integrations/salla/callback`
- Webhook: `https://trbhh.sa/api/integrations/salla/webhooks`
- الإدارة: `https://trbhh.sa/admin/suppliers/integrations`
- عامل المطابقة: `POST https://trbhh.sa/api/internal/suppliers/reconcile`

هذه مسارات فعلية في الكود، **وليست تأكيدًا أنها منشورة الآن**. عند اختبار نسخة ذات نطاق جانبي، استخدم أصل ذلك النطاق في `SUPPLIER_PUBLIC_ORIGIN` ونفس المسارين بالضبط في Salla. لا يستنتج الخادم الأصل من Host أو query parameters. Callback يتطلب جلسة مسؤول مخول في المتصفح الذي بدأ الربط.

## متغيرات البيئة (القيم خارج Git والمحادثة)

| المتغير | الغرض |
|---|---|
| `SUPPLIER_PUBLIC_ORIGIN` | أصل HTTPS للنسخة التي تستقبل التفويض، دون مسار |
| `SALLA_CLIENT_ID` | معرّف التطبيق الخاص |
| `SALLA_CLIENT_SECRET` | سر التطبيق؛ خادم فقط |
| `SUPPLIER_TOKEN_ENCRYPTION_KEY` | مفتاح مستقل AES-256-GCM: 32 بايت ممثلة بـ64 حرف hex |
| `SALLA_WEBHOOK_SECRET` | سر توقيع Webhook المطابق لإعداد Salla |
| `SUPPLIER_RECONCILE_SECRET` | سر Bearer عشوائي بطول32 حرفًا على الأقل لعامل المطابقة |
| `SUPPLIER_ALLOW_LIVE_ORDERS` | يبقى `false` خلال الاختبار؛ ليس كافيًا لتشغيل الطلبات الحقيقية |

أضيفت المتغيرات إلى `.env.example` وتمرير Docker Compose. توكنات كل متجر مشفرة مع AAD يربطها بالمورد والمتجر. لا يعاد استخدامها بين المتاجر. احتفظ بنسخة آمنة من مفتاح التشفير خارج المستودع؛ تغييره دون ترحيل يعطل فك توكنات الاتصالات ويستلزم إعادة ربطها. لا يُستخدم AUTH_SECRET لتشفير الموردين.

## خطوات Salla اليدوية

1. احتفظ بـCustom Authentication Mode؛ لا تحول إلى Easy Mode من أجل هذا الاختبار.
2. انشر فرع الاختبار في بيئة معزولة بعد نسخة احتياطية، وأدخل أسرار الخادم عبر مدير الأسرار/بيئة الاستضافة لا Git ولا لوحة المنتج.
3. أضف Callback المطابق لأصل النسخة المنشورة إلى Callback URLs. لا تستخدم رابط Salla الافتراضي القديم.
4. اضبط استقبال Webhooks على المسار أعلاه، باستراتيجية **Signature** وبالسر نفسه المخزن في الخادم.
5. راجع الصلاحيات الفعلية للتطبيق عند الاختبار: منتجات وطلبات وشحن بحسب عمليات القراءة المطلوبة، و`offline_access` للتجديد. لا تمنح صلاحيات غير لازمة ولا ترسل التطبيق للمراجعة.
6. اختر متجرًا تجريبيًا ثم ابدأ الربط من إدارة تربح في المتصفح نفسه. بيانات المتجر تؤخذ من `data.merchant.id` عبر طلب موثق إلى Salla، لا من مدخل المستخدم أو رقم الموظف.

الأحداث المدعومة: `product.created`, `product.deleted`, `product.quantity.low`, `product.price.updated`, `product.status.updated`, `product.image.updated`, `product.category.updated`, `product.brand.updated`, `product.tags.updated`, `product.channels.changed`؛ مع قبول `product.updated` و`product.available` القديمين. الطلبات `order.created`, `order.updated`, `order.status.updated`, `order.cancelled`؛ الشحن `shipment.creating`, `shipment.created`, `shipment.updated`, `shipment.cancelled`.

لا تفترض وجود حدث لكل تغيير مخزون؛ المطابقة الدورية لازمة. Webhooks الجزئية تحفز إعادة قراءة المورد ولا تستخدم كإثبات دفع مصرفي. أحداث Easy-mode التي تحتوي توكنات لا تُخزّن ولا تُستخدم في هذا Custom flow.

## عامل المطابقة والتشغيل

جدولة خارجية كل خمس دقائق تستدعي مسار reconcile بـPOST وترويسة `Authorization: Bearer <السر من بيئة المجدول>`، دون وضع السر في URL أو سجل الأوامر. لم تُنشأ جدولة إنتاج تلقائيًا في هذا التغيير. الاستجابة أعداد فقط. تُعالج خمس رسائل كحد أقصى، ثم طلبات مدفوعة محدودة وتتبع محدود واتصال كتالوج واحد، مع مهلة مشتركة45 ثانية.

المزامنة اليدوية محدودة100 صفحة، وحجم صفحة Salla لا يتجاوز60. الأخطاء تسجل رموزًا ثابتة فقط. الرسائل المكررة تُحفظ مرة واحدة، وتُعاد المحاولة تدريجيًا حتى8 مرات؛ حالات الفشل النهائية تحتاج مراجعة، بينما المطابقة الدورية تعوض الأحداث الفائتة. توقيع HMAC-SHA256 يتحقق على البايتات الأصلية قبل تحليل JSON؛ حد الجسم1MiB، ورفض الطابع الزمني المستقبلي/الأقدم من7 أيام. لا تخزن أجسام Webhook الخام أو بيانات العميل في سجل الأحداث.

تجديد التوكن أحادي الاستخدام: claim دائم يمنع التوازي، واستبدال ذري للزوج. فقدان/غموض نتيجة التجديد يطلب إعادة الربط ولا يعيد إرسال Refresh Token القديم. إيقاف/فصل الاتصال أو بدء تفويض أحدث يبطل اكتمال محاولات OAuth القديمة بواسطة generation.

## اختبار متجر تجريبي دون شراء

1. ابدأ بقاعدة اختبار معزولة، لا نسخة مفتوحة لبيانات العملاء الحقيقية، وبمفاتيح الدفع والإشعارات المالية معطلة.
2. أضف موردًا من `/admin/suppliers` ثم افتح «تكامل Salla وكتالوج الموردين». اختر Salla وDevelopment، فعّل المورد واحفظ.
3. اضغط ربط متجر Salla وأكمل التفويض بمتجر تجريبي. تحقق من Connected، ثم فعل المزامنة واضغط «مزامنة الآن».
4. تحقق من الصور/SKU والوصف والأسعار والمخزون والخيارات. المنتج الجديد يجب أن يكون غير نشط ومخفيًا. CJ/Other معرّفات قابلة للتوسعة لكن موصلاتهما لم تُنفذ ولا تدعي الاتصال.
5. اختبر منتجًا بسيطًا: مصدر50 وتكلفة40 وبيع47 تعطي ربح7 ريالات. أعد المزامنة بعد تغيير المصدر؛ تكلفة40 وبيع47 واختيار الإخفاء يجب ألا تتغير. السياسة لا يعاد تطبيقها إلا بحفظ المسؤول.
6. جرّب الإيقاف/الإخفاء الفوري دون تغيير السعر، الصيانة، تعطيل المورد، وفصل الاتصال. لا يجب أن تعيد المزامنة نشر سلعة مخفية. إعادة التنشيط لا تعيد تشغيل السلع التي عطلت احترازيًا تلقائيًا.
7. سجل حجز50 وحدة بسعر35 وشريحة/حجز تالٍ بسعر32. إعادة إرسال نفس النموذج لا تكرر الحجز. الحجز المحلي المؤقت يحتسب منفصلًا عن المتبقي؛ استهلاكه يكون بعد إيصال دفع موثق فقط.
8. اختبارات الطلبات الآلية تستخدم بوابة fixture محلية وإيصالًا اصطناعيًا داخل قاعدة الاختبار؛ لا يوجد زر إداري لتحويل طلب حي إلى مدفوع. لا تنشئ شراءً حقيقيًا لمحاولة اختبار ذلك.
9. أرسل Webhooks موقعة من أدوات Salla التجريبية؛ تحقق من المزامنة ثم أعد الحدث. لا يتكرر القيد. حالات الشحن تظهر للمالك فقط ولا تكشف تكلفة المورد.
10. تأكد من فشل التوقيع الخاطئ ومن رد401 للمطابقة دون السر، ومن بقاء طلب المورد محجوبًا في Live. لا تفعّل Production قبل إكمال تجربة OAuth الحقيقية على متجر تجريبي والفحص البصري.

## التسعير والمخزون وحدود الإصدار

- لا توجد زيادة CJ بنسبة30% على Salla. السياسات: يدوي/سعر المصدر/خصم ثابت/نسبة بنقاط أساس، مع حد سعر وربح يرفض المخالفة. الأسعار أعداد هللات صحيحة وسجل تغييرات مستقل.
- المخزون المستورد لا يزيد مخزون سلعة منشورة تلقائيًا؛ تخفيض المصدر يُطبّق تحفظيًا بعد خصم المحجوز محليًا والالتزامات المدفوعة غير المكتملة. إعادة التزويد تراجع إداريًا من إدارة السلع الحالية، ويظل checkout محكومًا بكمية المصدر الحالية. هذا تحفظ مقصود حتى التحقق من توقيت حسم مخزون المورد بعد التنفيذ.
- المنتجات متعددة الخيارات تُستورد للمعاينة، **ولا يسمح بشرائها** قبل بناء اختيار وربط variant صحيح في checkout الحالي. كذلك الكميات غير المعروفة لا تتحول إلى مخزون غير محدود افتراضيًا.
- حجز المخزون هنا اتفاق مسجل في تربح، وليس حجزًا أو دفعًا مثبتًا لدى Salla. أنواع prepaid/commitment مستقلة. تستخدم أجزاء الحجز بالتتابع ثم التكلفة العادية/شريحة الكمية. إجمالي تكلفة الطلب دقيق؛ متوسط الوحدة القديم مقرب للأعلى فقط للعرض عند تعدد أسعار السطر، وتحتفظ لقطة الطلب بأجزاء التكلفة الدقيقة.
- طلب المورد الداخلي قبل الدفع هو لقطة محلية `awaiting_payment`، لا طلب خارجي. الإيصال الموثق وحده ينقله إلى pending؛ المحاكاة terminal ولا تتحول إلى طلب حقيقي لاحقًا. المورد الموقوف أو المنتج الموقوف يمنع dispatch.
- Salla create-order يحتاج بيانات عميل وشحن/ناقل وعنوان وطني وعقد دفع محدد. لا نختلق بيانات بنك المورد ولا نساوي دفع تربح بتسوية المورد. لا توجد ضمانة idempotency موثقة لـPOST orders العادي، لذلك الإرسال الحقيقي ما زال محجوبًا؛ عند تنفيذه لاحقًا يلزم durable claim وحالة unknown دون إعادة إرسال غامضة.
- التتبع يدعم أسماء الشركات والأرقام والحالة والطابع الزمني، مع إشعارات `in_app` مقتضبة لا تعيد الخصم. WhatsApp/SMS للشحن ليسا موصلين جديدين في هذا الإصدار؛ إشعارات الدفع الحالية لم تُستبدل.

- تعديلات ضيقة في `commerce/orders.ts` للحجز/لقطة المورد/الاستهلاك/التحرير داخل معاملات الدفع الحالية؛ لم يتغير `commerce/runtime.ts` أو محول البنك.
- الأدلة الثلاثة `/guide`, `/guide/store`, `/admin/guide` محدثة، وكذلك إعدادات Docker وأمثلة البيئة واختبارات الترقية.

## الفحص المحلي

نتيجة التشغيل في19 سبتمبر2026: **783 اختبار وحدة ناجحًا،8 متجاوزة؛24 اختبار MySQL للتكامل؛53 اختبار MySQL للتجارة الحالية؛اختبار ترقية واحد يحفظ البيانات والجلسات القديمة**. Typecheck وPrisma generate وbuild نجحت. ESLint بلا أخطاء مع5 تحذيرات موجودة خارج ملفات التكامل؛ البناء يسجل تحذيرات middleware/storage القديمة. لم يتم اختبار OAuth مع متجر Salla حقيقي أو إجراء فحص بصري؛ تشغيل خادم المعاينة المحلي رُفض بسياسة بيئة التنفيذ. اختبارات Callback تستخدم جلسات/أسرار اصطناعية وHTTP fixtures، وليست إثبات ربط حي.

الأوامر المكافئة لسكربتات المشروع، عند تعطل غلاف pnpm المحلي:

```text
node node_modules/prisma/build/index.js generate
node node_modules/typescript/bin/tsc --noEmit
node node_modules/eslint/bin/eslint.js .
node node_modules/vitest/vitest.mjs run
node node_modules/next/dist/bin/next build
```

اختبارات MySQL اختيارية ولا تقبل إلا127.0.0.1:33309 وقاعدة fixture المحددة، تنشئ قاعدة جديدة وتزيلها فقط إذا أنشأتها بنفسها. ملفات الإعداد: `vitest.suppliers.config.ts` و`vitest.commerce.config.ts`. نتائج التشغيل النهائية في تسليم المهمة؛ لا تعامل نجاح unit tests كإثبات OAuth حي أو مرور UI.
