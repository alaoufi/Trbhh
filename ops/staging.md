# بيئة التجريب (Staging) — رابط سرّي غير معلن لتجربة الميزات قبل الإطلاق

الهدف: تجربة أي ميزة (الدفع الإلكتروني، الوحدة العقارية، أي تغيير) على **رابط منفصل محمي
بكلمة مرور** (مثل `https://beta.trbhh.com`)، بقاعدة بيانات **منفصلة تماماً** عن الموقع الحيّ —
فلا يتأثّر الإنتاج ولا بيانات الأعضاء، ولا يراه أحد من العامة.

النموذج: **الإنتاج** يُنشر من فرع `claude/hostinger-vps-project-amw8vb` → `trbhh.com`.
**التجريب** يُنشر من فرع `staging` → `beta.trbhh.com` (دليل ومشروع Docker وقاعدة منفصلة على
نفس الخادم). الملفّان `docker-compose.staging.yml` و`.github/workflows/deploy-staging.yml`
جاهزان — يتبقّى تجهيز الخادم مرّة واحدة.

---

## تجهيز لمرّة واحدة (على الخادم ومزوّد النطاق)

### 1) DNS — نطاق فرعي
من مزوّد النطاق (Hostinger): أضِف سجل **A** باسم `beta` يشير إلى **IP الخادم نفسه**
(نفس IP الذي يشير إليه `trbhh.com`).

### 2) قاعدة بيانات تجريب منفصلة
أنشئ قاعدة فارغة جديدة، مثلاً `trbhhdb_staging`، بمستخدم لها. (التطبيق يُنشئ الجداول تلقائياً
عند أول إقلاع — لا حاجة لاستيراد شيء. تبدأ فارغة، وتُسجّل فيها حسابات وإعلانات تجريبية.)
> لا تستخدم قاعدة الإنتاج إطلاقاً — الهدف العزل التام.

### 3) دليل التجريب على الخادم
```bash
cd /root
git clone <رابط المستودع> trbhh-staging
cd trbhh-staging
git checkout staging          # بعد إنشاء الفرع (الخطوة 5)
```

### 4) ملف .env الخاص بالتجريب
أنشئ `/root/trbhh-staging/.env` (منفصل عن ملف الإنتاج):
```dotenv
APP_PORT=3081
DATABASE_URL=mysql://<user>:<pass>@host.docker.internal:3306/trbhhdb_staging
AUTH_SECRET=<ولّد جديداً: openssl rand -hex 32>   # سرّ مختلف عن الإنتاج
COOKIE_SECURE=true                                 # لأن beta ستكون على HTTPS
# اترك بقية إعدادات الوسائط القديمة فارغة (قاعدة التجريب نظيفة):
LEGACY_MEDIA_BASE=
LEGACY_LOCAL_DIR=
NEXT_PUBLIC_MEDIA_BASE=
```

### 5) فرع staging
أطلب مني إنشاء فرع `staging` ودفعه (أو): 
```bash
git checkout -b staging origin/claude/hostinger-vps-project-amw8vb
git push -u origin staging
```
> بمجرّد وجود فرع `staging` والدليل `/root/trbhh-staging`، يصبح النشر التلقائي فعّالاً.

### 6) البروكسي العكسي + SSL + كلمة مرور (من لوحة تحكّم الخادم)
في لوحة الخادم (CloudPanel/aaPanel/إلخ):
- أضِف موقعاً/نطاقاً: `beta.trbhh.com` → **Reverse Proxy** إلى `http://127.0.0.1:3081`.
- فعّل شهادة **SSL (Let's Encrypt)** له.
- فعّل **Basic Auth (كلمة مرور)** على الموقع — فلا يفتحه إلا من يملك الكلمة (غير معلن).

---

## الاستخدام اليومي (بعد التجهيز)

1. أطوّر الميزة وأدفعها إلى فرع `staging` → تُنشر تلقائياً على `beta.trbhh.com`.
2. تجرّبها أنت على الرابط السرّي (تدخل بكلمة مرور Basic Auth أولاً).
3. عند رضاك، أدمج التغيير إلى فرع الإنتاج → يظهر على `trbhh.com` الحيّ.

هكذا: **لا شيء يصل الموقع الحيّ قبل أن تجرّبه وتوافق عليه.** ومثالياً للدفع (وضع تجريبي +
بطاقات اختبار على HTTPS) وللوحدة العقارية (تجربتها كاملة قبل تفعيل الترخيص وتفادي الغرامة).

## ملاحظات
- النشر التلقائي للإنتاج والتجريب يستخدمان نفس أسرار الخادم (VPS_HOST/USER/PORT/KEY).
- سرّ اختياري `STAGING_DIR` يغيّر دليل التجريب إن رغبت (الافتراضي `/root/trbhh-staging`).
- بيئتان معزولتان: حاويات وقاعدة ووسائط وأسرار منفصلة — تجربتك لا تمسّ الإنتاج أبداً.
- تحديث ملفّات `ops/**` لا يستدعي أي نشر (مستثناة في كلا المسارين).
